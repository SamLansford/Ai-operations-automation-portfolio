# Pre-publication review

Date: 2026-11-12. Status: PARTIAL — research and source-inspection findings; no live audit, deployment, workflow execution, or runtime test performed today.

## Evidence boundary

The coordinating agent's source inspection reports a loopback-only backend bridge, submit disabled on public hosts, an embedded same-origin `/demo-frame/index.html`, and a global generated `dist/_headers` policy containing `frame-ancestors 'none'`. The local server does not apply that policy. Latest integrated browser tests mocked backend responses; the recorded real ticket predates the embed. The 48/48 report predates the latest realistic examples. These are supplied source/history findings, not independent runtime verification by this research task. Profile email/resume are null; frame heights are fixed at 1750px/2650px. Their practical effects remain untested today.

## Five highest priorities

1. **P0 — Resolve the iframe/header conflict before publication.** Cloudflare Pages applies `_headers` rules to static assets. If the global policy reaches the demo child response, `frame-ancestors 'none'` prevents embedding, including same-origin embedding. Scope an appropriate policy to the child (for example allow only `'self'`) without retaining a simultaneous denying policy, or remove the iframe. Preserve restrictive framing on other pages. Verify actual child response headers and rendering in a host-equivalent preview. This is a source-supported deployment failure prediction, not an observed deployed failure. Sources: [Cloudflare headers](https://developers.cloudflare.com/pages/configuration/headers/), [MDN frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors).

2. **P0 — Choose and label the public demo mode honestly.** Publish the static portfolio with a clearly identified local-only demo or recorded/synthetic walkthrough unless a separate public backend is intentionally provisioned. Static hosting serves HTML/CSS/JavaScript; it does not provide the running n8n/MySQL/Ollama stack. A public live version needs a separately reachable, maintained backend and unavailable/timeout handling. Do not present mocked browser checks or the earlier real ticket as evidence that the current embedded path completes a real workflow. Before claiming live operation, verify the complete embedded submission through n8n, database persistence, and returned UI result; record execution ID and HTTP statuses. Source: [GitHub Pages architecture](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

3. **P1 — Establish server-side protection before any public submission endpoint.** Use HTTPS, endpoint authorization where access is restricted, strict method/content/schema/length validation, request/concurrency limits, and explicit timeouts before expensive Ollama work. Return 429 for rejected excess requests. Keep n8n management, MySQL, and Ollama interfaces private; keep credentials on the server. Treat CORS as a browser policy rather than authentication. Native n8n webhook authentication is available; inspect the deployed version/configuration rather than assuming defaults provide these protections. None of these controls has been runtime-audited here. Sources: [OWASP REST security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html), [n8n Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/), [n8n security](https://docs.n8n.io/hosting/securing/overview/).

4. **P1 — Minimize and explain demo data.** Prefer synthetic tickets; ask users not to submit personal information or secrets. Collect only fields needed for the demonstration. Before public collection, state where text is processed/stored, retention/deletion arrangements, and relevant hosting/logging providers; review n8n execution payloads, application logs, database rows, screenshots, and exports. Configure retention deliberately: n8n execution pruning does not establish a retention policy for MySQL or other logs. These are engineering recommendations, not a jurisdiction-specific legal compliance determination. Sources: [W3C Privacy Principles](https://www.w3.org/TR/privacy-principles/#data-minimization), [n8n execution data](https://docs.n8n.io/hosting/scaling/execution-data/).

5. **P1 — Complete employer-facing accessibility and discovery checks.** Manually verify keyboard navigation and visible focus across the iframe, input labels, accessible status/error announcements, contrast, text zoom/reflow, mobile layout, and no clipped results at the fixed frame heights. Provide a descriptive iframe title and a usable standalone demo link. Resolve missing contact/resume destinations before making those calls to action. Confirm a descriptive page title, useful main-page text/headings, crawlable project links, and production indexing/canonical settings after choosing the final URL. Do not claim WCAG compliance or search indexing from source inspection or automated checks alone. Sources: [WCAG 2.2 reference](https://www.w3.org/WAI/WCAG22/quickref/), [W3C form notifications](https://www.w3.org/WAI/tutorials/forms/notifications/), [Google SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide).

## Recommended release gate

Resolve the header conflict, select the public demonstration mode, and run a host-equivalent visual/accessibility review. If live submission is intended, additionally verify the complete current embedded path against the DEV workflow and confirm backend protections and retention before enabling it. This review changes no implementation and grants no production-change authorization.
